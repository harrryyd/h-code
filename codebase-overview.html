T3 Code / High-Level Overview

A coding-agent app with a browser front end and an event-driven server core.

If you know Spring Boot, the easiest mental model is: React UI as the web client, Node/Effect server as the application service layer, WebSocket RPC instead of REST for most live operations, and SQLite-backed projections acting like read models built from domain events.

1. What Lives Where

Core Apps
apps/server The backend process. It serves the UI, owns WebSocket RPC, starts provider runtimes, persists orchestration state, and turns raw provider activity into stable domain events.
apps/web The browser UI. It connects to the server, subscribes to live updates, keeps a client-side store, and renders chat, threads, plans, diffs, terminals, and settings.
apps/marketing Separate marketing site. Not part of the runtime flow of the coding app.
Shared Packages
packages/contracts Shared schemas and types. Think of this as the shared DTO/API contract module.
packages/shared Reusable runtime helpers used by both server and web.
packages/client-runtime Small client helpers for environment/thread/project identity and scoping.

2. Spring Boot Translation

What feels familiar

  • Layers in the server are similar to Spring bean wiring/configuration.
  • Services are real application services with typed interfaces.
  • SQLite persistence plus projection tables plays the role of repositories/read models.
  • packages/contracts is the shared API model package you might share between modules.

What is different

  • The code is strongly event-driven: commands produce domain events, then projections are updated.
  • Most live app behavior uses WebSocket RPC and subscriptions, not controller-style REST endpoints.
  • The server talks to coding providers as long-running runtime sessions, not short request/response calls.
  • The frontend keeps a substantial in-memory state store because the UI is continuously streaming.

3. Main Runtime Flow

1

Browser starts

apps/web/src/main.tsx boots React and the router. The root route then prepares auth, environment state, tracing, and WebSocket coordination.

2

Web UI opens a live connection

The client creates a WebSocket transport and RPC client. The runtime service keeps that connection alive, reconnects when needed, and subscribes to shell-level and thread-level orchestration streams.

3

Server exposes one live API surface

apps/server/src/ws.ts is the main RPC boundary. You can think of it as the equivalent of a controller layer, except it supports streaming subscriptions in addition to command-style calls.

4

User action becomes an orchestration command

When the user creates a thread, sends a prompt, archives a thread, or similar, the server normalizes that input into an orchestration command and dispatches it through the orchestration engine.

5

Orchestration engine is the domain core

apps/server/src/orchestration/Layers/OrchestrationEngine.ts is the heart of the app. It validates commands against the current read model, writes domain events, updates projections, and publishes those events to subscribers.

6

Provider runtime does the actual agent work

The provider layer starts and manages long-lived sessions for Codex or other providers. ProviderService is the cross-provider facade; adapters hide the provider-specific protocol details.

7

Raw provider events are translated into app events

ProviderRuntimeIngestion listens to provider runtime events and turns them into stable orchestration events such as message updates, approval requests, plan updates, checkpoints, and session status changes.

8

Read models are pushed back to the UI

The server exposes a shell snapshot stream for the sidebar/list view and a thread detail stream for the open conversation. The client store applies those updates and React re-renders the page.

4. The Most Important Design Idea

The app does not let provider-specific runtime events directly drive the UI. Instead, provider events are first translated into a stable orchestration domain model, then projected into snapshots the UI can safely consume. That is the main reason the app can stay predictable under reconnects, partial streams, and session restarts.

5. Files Worth Reading First

Server

  • apps/server/src/server.ts for top-level runtime wiring.
  • apps/server/src/ws.ts for the live API boundary.
  • apps/server/src/orchestration/Layers/OrchestrationEngine.ts for the command → event → projection flow.
  • apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts for provider event translation.
  • apps/server/src/provider/Layers/ProviderService.ts for provider session orchestration.

Web

  • apps/web/src/routes/__root.tsx for app bootstrapping.
  • apps/web/src/environments/runtime/service.ts for connection and subscription management.
  • apps/web/src/store.ts for the main client state model.
  • apps/web/src/rpc/wsTransport.ts for the reconnecting WebSocket transport.

6. One-Sentence Summary

T3 Code is essentially a live, event-driven coding workspace where the server manages agent runtimes and converts everything into a stable orchestration model, while the React client stays subscribed to that model and renders the current project, thread, and agent state in real time.

Good next step: read ws.ts, then OrchestrationEngine.ts, then ProviderRuntimeIngestion.ts. That will reveal most of the application flow.
